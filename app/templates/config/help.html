Pipeline overview

Configure everything under Pipeline as a chain per source:

Source → Events → Rules → Actions

  1. Source — a webhook receiver or a poll that runs a typed poller on a schedule.
  2. Events — named types for that source (e.g. status.changed, on_success).
  3. Rules — which events (and optional conditions) should fire actions.
  4. Actions — update a Field, notify (ntfy/Gotify/Discord), call a URL, send a browser notification, or (when enabled) run a local script when the rule matches.

Typical setup: add a source, define event types, create a rule for those types, then add actions on the rule. Confirm results on Events.

Fields

Fields store values you can show on the dashboard. Actions update them when rules match. They live on the Pipeline page (not tied to one source).

TypePurpose
Logbook Growing list of entries with a max size. Good for recent activity.
Value A number — actions can add, subtract, set, or reset.
Text A single text value set from a template.
Toggle On/off state — actions can set Fixed or Switch.

Create a Field first (note its slug). Use that slug in an “Update field” action, and in dashboard templates as {{ '{{ slug.value }}' }} under Dashboard Layout (Fields button lists slugs). On a Logbook, use Recent to inspect the latest entries, or Clear to wipe them. Series graphs need a path after the slug (e.g. usd_prices.rate); for a bare number entry use slug.value (same as templates).

Rule matching

When an event arrives, rules run in priority order (lower numbers first). A rule matches only if all of these pass:

  1. Source — the rule belongs to that event’s source.
  2. Event types — leave the list empty to match all types for that source; otherwise the event’s type must be selected.
  3. Conditions — see below; with no conditions, every event that passed the filters above matches.

Then each linked active (not paused) action on the rule runs.

Pause an event type, rule, or action from the pipeline chain. Paused event types are still stored when they arrive; rules do not run for them.

Rule conditions

Conditions filter on values in the event. In the rule dialog you build rows of Field + Operator + Value. Use Advanced (JSON) only if you need matching the form can’t build.

Behavior

  • Empty (no rows) — match all events that already passed source and event-type filters.
  • All must match — every condition row has to pass.
  • Missing or invalid data — for most operators, a missing field or bad value means the condition does not match. Not equal also matches when the field is missing.
  • Nested values — use a simple name like severity, or a path like status.code if the event nests data.
  • List indexes — data.0.id reads a fixed position in a list.
  • Any list item — data.*.status matches if any element’s status matches. Several paths that share the same list (e.g. data.*.base and data.*.quote) must all match on the same element.
  • Actions and templates — when the rule’s conditions used *, the same list row is used for * in field keys and {{ '{{…}}' }} placeholders (value.*.rate is the matched pair’s rate). If conditions did not use *, * means the first item. Each action still runs once.

Operators

OperatorMeaning
Equals (=) Exact match (numbers compared as numbers when the value looks numeric)
Not equal (≠) Not equal — including when the field is missing
Greater than (>) Numeric comparison
Less than (<) Numeric comparison
Contains Substring appears in the text form of the value
Matches pattern (regex) Regular expression against the text form of the value

Combining conditions

Multiple rows on different fields all must match. Prefer one clear operator per field in the visual editor. Use Advanced (JSON) for unusual shapes (for example a numeric range).

Advanced JSON examples 
{}
# match all events for the selected types

{"severity": "high"}
# only when severity is exactly "high"

{"amount": {"gt": 100}, "currency": "USD"}
# amount > 100 AND currency equals USD

{"status": {"not": "ok"}}
# status is anything other than "ok" (including missing)

{"status": {"contains": "fail"}, "code": {"regex": "^5\\d\\d$"}}
# status contains "fail" AND code looks like 5xx

{"data.*.status": "fail"}
# any element in data[] has status "fail"

{"data.*.base": "USD", "data.*.quote": "EUR"}
# one element in data[] has base USD and quote EUR (same row)

Actions

Each action has a type and settings for that type. The Pipeline chain shows what it does (for example, which Field it updates).

TypeWhat it does
Update field Writes to a Field (append, set, count, or toggle). Skips when the new value matches what is already stored. For logbooks, see value source.
Notify Sends a message via ntfy, Gotify, or Discord (title/body templates). Thin wrapper over Call URL.
Call URL Calls a URL with optional auth, headers, templated body (JSON or plain text), presets, and optional HMAC signing. See auth & signing below.
Browser notification Sends a browser notification. Title and body can include placeholders like {{ '{{source}}' }}.
Local script Runs a shell one-liner or argv list on this host. Requires PARA_SCOPE_ALLOW_LOCAL_ACTIONS=1; optional path allowlist via PARA_SCOPE_LOCAL_ACTION_ALLOWLIST.

Logbook value source

When an Update field action targets a logbook, choose how the entry value is built. Reserved name field is the current stored value (paths, maths, and shapes).

ModeWhat it storesSyntax
Entire event Whole event data object —
Value from event Typed path, maths number, or compiled JSON shape path / expr / {…} or […]
Template Always a string text with {{ '{{ path }}' }} / {{ '{{ expr }}' }}

Value from event examples:

  • Path (keeps objects/lists): payload.sensor
  • Maths: temp * 1.8 + 32 or 1 / value.*.rate — ops + - * / %, functions abs, round, min, max. In maths, * is the list row matched by the rule’s conditions (same as path-only).
  • JSON shape (string leaves = path, maths, or literal text):
{{ '{' }}
  "label": "Sensor A",
  "celsius": "temp",
  "fahrenheit": "temp * 1.8 + 32",
  "raw": "payload.sensor"
}

Call URL, notify, and browser notification templates stay strings. Use Value from event on a logbook when you need typed numbers or a rebuilt object.

Call URL — auth & signing

When the action runs, Para-Scope can authenticate and/or sign the outbound request.

Auth modeWhat it does
None No credential headers.
Bearer token Sends the stored secret in a header (default Authorization: Bearer …). Header name and prefix are configurable.
API key + secret Sends two custom headers (key and secret). Useful for APIs that don’t use Bearer.

Optionally enable HMAC-SHA256 signing. Para-Scope signs METHOD\nURL\ntimestamp\nbody (compact JSON with sorted keys for POST/PUT/PATCH; empty body for GET/DELETE) and adds:

  • X-Call-Signature — hex digest (header name configurable)
  • X-Call-Timestamp — unix seconds (header name configurable)

Signing uses the action’s secret (or the second secret when using API key + secret). The destination verifies the signature the same way.

Webhooks

Send events to your source’s webhook URL. Create a Webhook source on the Pipeline page.

  • Once you’ve added any event type (except always), senders must include a matching type.
  • Add an event named always to also run on every delivery (senders don’t send always — Para-Scope emits it).
  • Choose a Webhook verification mode and, when needed, a credential in the Webhook secret field.

Accepted deliveries return 202. Discord’s endpoint handshake (PING) returns 200. PayPal accepts any 2xx, so 202 is fine.

On the Pipeline page, use Recent for the last few events, and Sample on an event type for that type’s latest payload (handy when writing rules). Each source keeps at most 500 events; older ones are removed automatically.

Verification modes

ModeCredentialHow it verifies
Shared-secret HMAC Shared secret (optional) With a secret: requires X-Webhook-Timestamp and X-Webhook-Signature (HMAC-SHA256 of {timestamp}.{raw_body}). Without a secret: unsigned traffic is allowed (local/dev).
Stripe Stripe signing secret Stripe-Signature header (t=…,v1=…), HMAC over {t}.{body}.
GitHub / Gitea Webhook secret X-Hub-Signature-256 = HMAC-SHA256 of the raw body (same scheme for both).
Slack Slack signing secret X-Slack-Signature + X-Slack-Request-Timestamp; HMAC over v0:{timestamp}:{body}.
Discord App public key (hex) Ed25519 over {timestamp}{raw_body} using X-Signature-Ed25519 and X-Signature-Timestamp.
PayPal Client secret (+ webhook ID & client ID in source config) Calls PayPal’s verify-webhook-signature API with the delivery headers and event body (sandbox or live).

Signed providers also reject duplicate deliveries (replay protection) within a short window.

Discord notes

  • Paste the Discord application public key into the Webhook secret field (not a shared HMAC secret).
  • Discord’s PING (type: 1) is answered with {"type": 1} and never becomes an event.
  • Other interactions map to event types: application_command, message_component, application_command_autocomplete, modal_submit. Register those names on the source to match slash commands, buttons, and modals.

PayPal notes

  • Set webhook ID, client ID, and environment (sandbox/live) on the source.
  • Store the PayPal client secret in the Webhook secret field.
  • Register event types that match PayPal’s event_type values (e.g. PAYMENT.SALE.COMPLETED).
For senders (generic HMAC)
  • Send POST /webhook/{slug} with a JSON body.
  • Type via the X-Event-Type header, or body field event_type / type.
  • With a secret: also send X-Webhook-Timestamp (unix seconds) and X-Webhook-Signature. Sign with HMAC-SHA256 of {timestamp}.{raw_body} (hex; optional sha256= prefix).

Polling

Poll sources run one poll subtype on a schedule (interval or cron) and feed the same pipeline. Create or edit the source, choose a category, then choose the subtype and fill in its typed fields.

CategoryExamples
URL / HTTP GET, POST, PUT, DELETE
System Host snapshot, failed systemd units, recent journal errors
Connectivity / Reachability TCP connect, ICMP ping, DNS resolve, TLS cert expiry
Storage / Filesystem Free space, backup age
Application / Domain Database health, git status, log pattern watch, Home Assistant snapshot, local LLM status
External RSS / Atom change, IMAP unread, public endpoint status, domain expiry
Current shipped poll subtypes
  • URL / HTTP — http_get, http_post, http_put, http_delete
  • System — system_snapshot, systemd_failed_units, journal_recent_errors
  • Connectivity / Reachability — tcp_connect, icmp_ping, dns_resolve, cert_expiry
  • Storage / Filesystem — disk_free_space, backup_age
  • Application / Domain — database_health, git_status, log_pattern_watch, home_assistant_snapshot, local_llm_http_status
  • External — rss_atom_change, public_http_status, imap_unread, domain_expiry

A successful poll emits on_success by default, or another success type if that subtype exposes one. Failures emit on_failure. Add an event named always to also fire on every run.

HTTP poll authentication

URL / HTTP pollers can attach credentials from an encrypted poll secret. Choose an auth mode on the schedule:

Auth modeSecret formatWhat happens
Bearer token Raw token Sent as Authorization: Bearer … by default. Header name and prefix are configurable.
HTTP Basic username:password Standard Basic auth header.
OAuth2 client credentials client_id:client_secret Fetches an access token from the token URL (optional scope), caches it in-process, then sends it as a Bearer token.

Poll-specific secrets are stored encrypted. Some pollers also depend on host commands being present, and their failures will show up as poll errors.

Use Run now on a poll source to fire it immediately without waiting for the next interval or cron tick.

Planned / future integrations are documented separately in the design docs. They are not implied to be available just because a category exists.

Planned / future poll integrations
  • Container / runtime checks such as Docker snapshots
  • Fuller systemd snapshots beyond failed-unit summaries
  • SMART, ZFS, and Btrfs health checks
  • MQTT / local broker checks
  • Deeper queue integrations for Redis, RQ, and Celery

Browser notifications

To use browser notification actions:

  1. Ask your admin to enable browser notifications on the server.
  2. While logged in, click the bell icon in the page header to allow notifications.
  3. In the action, use placeholders like {{ '{{source}}' }} in title or body to insert event values.

Secrets

Credentials are stored encrypted (Fernet, keyed from PARA_SCOPE_SECRET_KEY). The same store covers:

  • Webhook sources — shared HMAC secrets, Stripe/Slack/GitHub signing secrets, Discord public key, PayPal client secret
  • HTTP polls — bearer tokens, username:password, or client_id:client_secret
  • Call URL actions — bearer tokens, API key/secret pairs, and optional HMAC signing keys

Secrets are never shown again after save. Replace by entering a new value, or clear the webhook secret from the source edit dialog.
