Pipeline overview

Configure everything under Pipeline as a chain per source:

Source → Events → Rules → Actions

  1. Source — webhook or poll endpoint that receives data.
  2. Events — named event types for that source (e.g. payment.paid, on_success).
  3. Rules — which events (and optional field conditions) should fire actions.
  4. Actions — what to do when a rule matches (log, notify, forward, etc.).

Typical setup: add a source, define event types, create a rule for those types, then add actions on the rule. Confirm results on Events.

Fields

Fields are global storage sinks on the Pipeline page (not per-source, and not the same as condition keys on event payloads). Actions write into them; dashboard widgets read them.

TypePurpose
logbook Append-only JSON entries with a max size. Widgets transform for display.
counter Numeric tally — field_push can increment, decrement (default delta 1), or reset.
value Single string — widgets may coerce for display.
toggle Boolean on/off state.

Create Fields first, then pick one on a field_push action and on Metric Graph / Logbook / Field Value widgets under Dashboard Layout.

Rule matching

When an event arrives, enabled rules are checked in order_index order. A rule matches only if all of these pass:

  1. Source — the rule’s source matches the event (rules are scoped to a source in the pipeline UI).
  2. Event types — empty selection means all types for that source; otherwise the event’s type must be in the list.
  3. Conditions — see below; empty conditions match everything that passed the filters above.

Then each linked enabled action on the rule is run.

Rule conditions

Conditions filter on fields in the event’s normalized_data (webhook JSON body, or fields extracted from a poll). In the rule dialog you build rows of Field + Operator + Value; they are stored as JSON under the hood.

Behavior

  • Empty (no rows / {}) — match all events that already passed source and event-type filters.
  • AND logic — every condition must match.
  • Fail-closed — missing fields, bad types, or invalid regex do not match.
  • Dotted paths — use severity or nested paths like _poll.outcome / _poll.response_time_ms.

Operators

OperatorMeaningStored JSON example
equals Exact match (numbers parsed when the value looks numeric) {"severity": "high"}
not Not equal (matches when the value differs, including if the field is missing) {"status": {"not": "ok"}}
gt Numeric greater than {"amount": {"gt": 10}}
lt Numeric less than {"amount": {"lt": 100}}
contains Substring in the string form of the value {"msg": {"contains": "error"}}
regex Python re.search against the string form {"code": {"regex": "^5\\d\\d$"}}

Combining conditions

Multiple rows on different fields all must match. Multiple operators on the same field (e.g. gt and lt) merge into one object: 

{"amount": {"gt": 10, "lt": 100}, "currency": "USD"}

Prefer one clear operator per field. If you mix equals and comparison ops on the same field in the visual editor, the last serialization wins. Use Edit as JSON on the rule form for unusual shapes.

Examples

{} 
# match all events for the selected types

{"severity": "high"}
# only when severity is exactly "high"

{"amount": {"gt": 100}, "currency": "USD"}
# amount > 100 AND currency equals USD

{"status": {"not": "ok"}}
# status is anything other than "ok" (including missing)

{"status": {"contains": "fail"}, "code": {"regex": "^5\\d\\d$"}}
# status contains "fail" AND code looks like 5xx

Actions

Actions have a type and type-specific params (no freeform name — the chain shows process → target). field_push picks a global Field; http_forward can attach secrets.

TypeParams
field_push Target Field + type-specific op. Event keys and counter deltas support dotted paths (e.g. _poll.response_time_ms).
http_forward URL, method, optional Bearer or Key+Secret credentials.
web_push Title, body, url — use {{ '{{source}}' }} / {{ '{{field}}' }} placeholders from event data.

Config may include retry_count to retry a failed action that many times after the first attempt.

Webhooks

Create a Webhook source, then POST /webhook/{slug} with a JSON body.

  • Once the source has event types, send the type via X-Event-Type header or body field event_type / type.
  • If the source has a webhook secret, send X-Webhook-Timestamp (unix seconds) and X-Webhook-Signature = HMAC-SHA256 of {timestamp}.{raw_body}. Without a secret, unsigned requests are accepted (ok for local/dev).

Each webhook event includes source and a _webhook object with slug, method, path, content_type, body_bytes, client, user_agent, event_type, correlation_id, signed, and delivery_lag_ms when X-Webhook-Timestamp is sent.

On the Pipeline page, use Recent on a source for the last few events, and Sample on an event type for that type’s latest normalized_data (handy when writing rules and field_push keys). Each source keeps at most 500 events; older ones are pruned automatically.

Polling

Poll sources run schedules in-process (interval or cron) and feed the same pipeline. Successful polls emit on_success (or handler_params.event_type when set); failures emit on_failure. An event type named always (not seeded by default) also fires on every run.

Each poll event includes source and a _poll object with schedule_id, status_code, attempts, outcome, and response_time_ms.

Schedule handler_params JSON supports json_path, event_type, headers, query, body, and optional auth_secret_id.

Web Push

For web_push actions:

  1. Set PARA_SCOPE_VAPID_PUBLIC_KEY and PARA_SCOPE_VAPID_PRIVATE_KEY in .env (optional PARA_SCOPE_VAPID_SUBJECT).
  2. Click the bell icon in the page header while logged in to enable notifications.
  3. Use {{ '{{field}}' }} or {{ '{{nested.path}}' }} placeholders in title/body/url from event data. Every event includes source (the Source name).

Secrets

Only http_forward actions attach credential secrets (Bearer or Key+Secret) in the action dialog. Values are encrypted with PARA_SCOPE_SECRET_KEY. Webhook source secrets and poll auth_secret_id use the same store. Never commit .env or secret values.
